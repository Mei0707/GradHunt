# IAM scope review

This review covers policies generated by the new CDK stack. Existing roles retain their pre-existing permissions; those policies cannot be certified least-privilege until the actual deployment is identified and audited.

| Principal | Allowed scope | Deliberate exclusions |
| --- | --- | --- |
| Gateway task role | `s3:GetObject`, `s3:PutObject` on the selected bucket's `resumes/*` objects | No bucket listing, object deletion, other bucket access, IAM, infrastructure management or Secrets Manager reads. Runtime secrets are injected by ECS. |
| ECS execution role | Pull the application image, create log streams/write events in the gateway log group; managed tasks read the selected runtime secret through ECS secret bindings | No application-level S3 access. Imported roles receive only additive repository/log permissions. Existing secret and KMS grants must already be correct. |
| GitHub release role | One repository's pull/push/DescribeImages actions; Describe/Update one ECS service; DescribeTaskDefinition in one family; PassRole for the exact task and execution roles | No CloudFormation, IAM editing, bucket data access, runtime secret reading or other-service updates. |
| GitHub OIDC principal | `aud=sts.amazonaws.com` and one exact protected environment subject | No wildcard owner, repository or subject trust. Account-specific immutable subject claims must be reflected explicitly. |
| Infrastructure operator | Reviewed CDK provisioning/bootstrap permissions supplied externally | Application CI does not receive these privileges. |

Two release actions require `Resource: "*"`: `ecr:GetAuthorizationToken` and `ecs:RegisterTaskDefinition`, which lack resource-level IAM scoping. `iam:PassRole` is restricted to the two configured roles and `iam:PassedToService=ecs-tasks.amazonaws.com`. Family-scoped describe permissions and service-scoped update permissions constrain the workflow's usable target. The register action can still create unused revisions; monitor CloudTrail and review the role as the deployment evolves.

The new S3 bucket blocks public access, requires TLS, encrypts objects, versions data, and retains the bucket on stack deletion. Imported buckets need their own review. Secrets are references in task definitions rather than image layers or GitHub variables. Production no longer derives its signing secret from an OpenAI key or logs email-action preview links when email configuration is missing.

Keep `TRUST_PROXY` disabled until task ingress is restricted to the ALB. Rate limiting now uses Express's trusted IP calculation instead of directly trusting arbitrary forwarded headers. Limits remain per task; use a shared limiter or edge controls if a global enforcement requirement is introduced.

The selected CloudFront endpoint uses a private ALB whose ingress is limited to the verified regional AWS-managed origin-facing prefix list. That path trusts exactly two proxy hops (`TRUST_PROXY_HOPS=2`); the direct-ALB option uses one. Application releases preserve the configured trust topology. The deployment preflight checks resource metadata and rejects placeholder configurations before CDK provisioning; it does not grant additional runtime IAM permissions.

Before enabling release access, inspect the concrete CDK diff and the existing task/execution roles. Confirm secret resource ARNs, any customer-managed KMS grants, account/region, task family, ECS service, OIDC subject and GitHub environment protections. Validate these policies in the actual account using IAM Access Analyzer/CloudTrail; synthesis tests establish generated policy shape, not effective live authorization. Review unused permissions after real workloads are observed.
